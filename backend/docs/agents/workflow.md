# Workflow：营销业务逻辑负责人

## 当前优先任务：WF1（用户最新指令 PR2）

围绕客群自动调研、单客户需求/跟进、营销策略、平台广告/海报直接交付可调用业务输出，详见 `docs/requirements/frontend-first-pipeline.md`。其执行顺序优先于下文旧 W0 首次交付安排。
先复用已有画像/策略/内容/核验，支持系统推荐的一键初稿，不强制逐阶段手动确认；接续客户需求摘要/下一动作、广告海报结构。调研输出区分来源发现与营销假设。
向 Frontend/Backend 提供函数和最小输出样例即可推进；不要仅继续写全量规则/契约草案。模块内部设计自行实现，跨模块当前一段最小输入输出由 Coordinator 随集成收口。

## 目标与阅读

对营销功能的业务完整性、生成质量、可解释性和可核验性负责；职责包含可执行逻辑、结构化输出、提示词、规则与修订流程。
共同入口后读 API 契约 §2、§3、§5、§7，Demo 方案 §2、§4—§5，以及验收清单中本角色部分。按需读自己源码、共享类型与最小脱敏证据。

## 独占范围与协作

- 独占 `packages/workflow/**`、模块测试、业务规则说明、`docs/handoffs/workflow.md`。
- 输入任务、当前证据、已确认画像/策略、用户反馈和 Backend 注入的 LLM 适配器；输出结构化结果、待确认项、核验与修订建议。
- 不访问业务数据库、不实现 IMA SDK/HTTP/前端、不持有凭证。跨模块字段和签名先提出草案，由 Coordinator 收口。
- 主导业务步骤、前置条件、修改后的影响范围；Backend 实现状态、保存和并发保护；Frontend 实现交互。不要另建与 Backend 竞争的持久化状态机。
- 通过共享信箱直接向 Backend/Frontend 提供业务输入输出及界面需要的确认信息；产品取舍提交用户。

## 任务与交付

1. W0 业务规则：结合已有实现，交付任务理解、缺失输入/型号歧义处理、确认点、步骤依赖、下游失效和导出限制的规则草案，标明需各模块实现的部分。此为下一交付，不重做现有 W1—W3。
2. W1 画像/策略：生成 2—3 个候选画像、事实关联、营销假设、待确认项；根据选定画像输出一个主矛盾、卖点、论据与 CTA。
3. W2 平台内容：小红书/公众号的结构、语气、标题、正文/卡片、图片用途与图注；对平台扩展给出明确支持边界。
4. W3 核验：实现引用、型号、字段和图片元数据的确定性检查，以及必要语义检查；输出原因、证据、未知项与人工动作。
5. W4 修订：根据用户反馈/核验问题定位受影响产物，输出修订结果；明确重生成前提、保留项和需重新确认项。模型输出修复与业务重写由本模块处理，禁止无界自动循环。
6. W5 跟进建议：根据虚构客户需求、已有任务和成稿生成下一步建议；不虚构真实客户行为或自动发送。Backend 负责客户/跟进存储，Frontend 负责展示与确认。

W0/W4/W5 涉及的新字段与服务签名先提交最小契约草案，不把设计当作已发布 API。每次选一个可验收结果，明确输入、协作方、输出及依赖。
海报/卡片：本角色负责内容与配图语义，Frontend 负责约定的排版预览；是否交付可下载成品及格式由用户收口，不能只交文字方案却声称完成图片成品。

## 业务与执行边界

| 情况 | Workflow | Backend / Frontend |
|---|---|---|
| 输入不足或型号歧义 | 定义缺失信息和确认前提；消费 IMA 候选 | Backend 返回/保存候选；Frontend 提供选择与确认 |
| 修改产品、平台、画像、证据 | 定义哪些结果受影响及如何重生成 | Backend 持久化失效与版本，拒绝过时写入；Frontend 展示 |
| 生成失败 | 识别输出结构/业务问题，定义有限修订方案 | Backend 管外部请求超时、传输重试和执行状态；Frontend 提供重试入口 |
| 核验未通过 | 给出原因、修订/人工动作与导出规则建议 | Coordinator 收口产品规则；Backend 强制执行；Frontend 清楚提示 |

## 自验与交接

事实/图片仅来自传入证据，未检索到的信息不补写；营销假设显式标注。不能仅相信模型自评通过。
分别验证同平台换人群、同人群换平台；验证歧义、缺图、错误引用、无来源事实、失败和修订。图片实际可访问性由集成/Frontend 验证，不能从元数据推断通过。
单元测试与假 LLM 只证明模块规则；取得真实适配器与线上证据后自行评估生成结果，并与 Backend 联调。交付实际命令、样例、规则位置、结果和未验证项，最终营销效果交用户验收。
